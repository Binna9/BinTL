### C. 칩 실행 · 산출물 슬롯 리팩터 (핵심)

**목표:** 칩 등록 = 레시피만. **실행**해야 파일/dataset 생김. 워크스페이스에서 재실행 시 **같은 슬롯** 덮어쓰기.

**3층 모델**

| 층 | 역할 | 저장 |
|----|------|------|
| 칩 (레시피) | extract/transform 정의 | `chips` + `chip_bindings` |
| 칩 실행 (이력) | 실행마다 append-only | `chip_runs` |
| 출력 슬롯 | workspace+chip당 stable dataset | `chip_output_slots` + `datasets` |

**Migration:** `crates/storage/migrations/0021_chip_output_slots.sql`

```sql
chip_output_slots (workspace_id, chip_id) → dataset_id
extracts.output_filename  -- one-off DB 내보내기용 사용자 파일명
```

**디스크 경로**

| 동작 | 경로 |
|------|------|
| DB **결과 내보내기** (standalone) | `data/extracts/databases/{extract_id}/{filename}.csv` |
| **칩 extract 실행** (워크스페이스) | `data/chip_outputs/{workspace_id}/{chip_id}/current.csv` (구분자에 따라 tsv/txt) |
| **칩 transform 실행** | `data/chip_outputs/{workspace_id}/{chip_id}/current.parquet` |
| standalone transform job | `data/outputs/{job_id}/result.parquet` (기존과 동일) |

**Storage (`crates/storage/src/chip_slot.rs`, `lib.rs`)**

- `upsert_chip_output_slot_dataset` — 성공 시 슬롯 dataset upsert + `chip_output_slots` 행.
- `set_extract_succeeded` — chip-linked run이면 extract id가 아닌 **슬롯 dataset id** 사용.
- `complete_chip_run_for_job` — run id 대신 슬롯 dataset id.
- `latest_chip_output_for_workspace(workspace_id, chip_id)` — 슬롯 우선, fallback은 예전 chip_runs.
- `linked_chip_run_for_extract` / `linked_chip_run_for_job`
- `insert_extract(..., output_filename)` — optional.

**Server**

- `crates/server/src/extract.rs` — chip run이면 slot 경로, standalone이면 `output_filename` 또는 테이블명 기본.
- `crates/server/src/chip.rs`
  - `queue_chip_run` 공통화.
  - `resolve_transform_input` → workspace-aware `latest_chip_output_for_workspace`.
  - `register_chip`: `place_on_workspace` 시 `run_after` 기본 true (`run_after: false`면 배치만).
- `crates/server/src/api.rs` — `CreateExtractBody.filename` / `name`.
- `crates/jobs/src/lib.rs` — chip-linked job은 출력을 slot 경로로.

**UI**

- `QueryPage`: 결과 내보내기 시 **파일 이름** 입력, `filename` API 전달.
- 칩 등록 힌트: “레시피 등록 → 워크스페이스 배치 후 실행하면 결과 생성·갱신”.
- `ui/src/types/chip.ts` — `run_after?`, `place_on_workspace?`.
- `ui/src/types/extract.ts` — `filename?`.

**delete_guard**

- `chip_output_slots`에 묶인 dataset 삭제 시 칩 이름으로 block 메시지.

## 2. 아직 안 맞는 부분 (내일 논의/작업 후보)

대화에서 **사용자 혼란**이 확인됨. 현재는 **의도적으로 두 갈래**지만 제품 관점에선 어색함.

| 경로 | 변환 화면에 뜨는 시점 | 파일 |
|------|----------------------|------|
| DB 결과 내보내기 | 즉시 (`datasets`, kind=database) | `extracts/databases/...` |
| 칩 등록만 | **안 뜸** (레시피만) | 없음 |
| 칩 워크스페이스 실행 | 실행 후 (`datasets`, 슬롯) | `chip_outputs/...` |

→ **같은 SQL**로 “내보내기 + 칩 실행” 하면 **파일·dataset 이중 적재** 가능.

**합치는 방향 (합의만, 미구현)**

> **파일 = dataset 하나.** 칩은 그 파일을 만드는/갱신하는 레시피.

- one-off 내보내기 vs 칩 슬롯 **경로 통합** (`artifacts/` 또는 전부 `extracts/` 아래).
- DB 화면: “내보내기” / “칩으로 저장” / “저장 후 실행” 의도 분리.
- 변환 페이지: 업로드·내보내기·칩 슬롯을 동일 “입력 파일” 목록으로 (출처는 메타만).

`docs/workspace.md`, `docs/transform.md`는 **슬롯 모델 반영 전** 내용이 섞여 있을 수 있음. 코드 기준은 이 문서 + migration 0021.

## 5. API 치트시트

```
GET/POST  /api/search/recent          최근 검색어 (POST: { "query": "..." })
POST      /api/extracts               body에 filename | name optional
POST      /api/chips                  register; place_on_workspace + run_after(optional)
POST      /api/chips/{id}/run         workspace_id, input_dataset_id?(transform)
```

Register body 예:

```json
{
  "name": "매출 추출",
  "kind": "extract",
  "workspace_id": "...",
  "place_on_workspace": true,
  "run_after": true,
  "extract": { "connection_id": "...", "source": { "type": "query", "sql": "..." }, "delimiter": ",", "header": true }
}
```

`run_after` 생략 + `place_on_workspace: true` → **기본 실행 큐**.
